\section{Семантика языка}
\label{section::Semantics}

Вопрос семантики -- вопрос, как интерпретировать присваивание в языке.
Есть два подхода:
\begin{enumerate}
\item Value Semantics.
\item Reference Semantics.
\end{enumerate}
Давайте начнем с первой.

\paragraph{Value Semantics}

В ней надо думать про переменные, как про стаканы, содержащие данные.
А присваивание -- это перекладывание данных.
\[
\xymatrix@R=15pt@C=15pt{
{}&{}&{\square}\ar@{|->}@/_10pt/[lld]+(0,4)\\
{\square}
{\save
[].[]*+[F--]\frm{}
\restore}
&{=}&{\boxtimes}\ar@{|->}[u]
{\save
[].[]*+[F--]\frm{}
\restore}
}
\]
И тут есть две вариации.
Данные могут копироваться.
Например, модель присваивания C++
\[
\begin{aligned}
\xymatrix@R=15pt@C=15pt{
{}&{}&{\square}\\
{\phantom{\boxtimes}}
{\save
[].[]*+[F--]\frm{}
\restore}
&{=}&{\boxtimes}\ar@{|->}[u]
{\save
[].[]*+[F--]\frm{}
\restore}
}
\end{aligned}
\quad\Rightarrow\quad
\begin{aligned}
\xymatrix@R=15pt@C=15pt{
{}&{}&{\boxtimes}\ar@{|->}@/_10pt/[lld]+(0,4)\\
{\square}
{\save
[].[]*+[F--]\frm{}
\restore}
&{=}&{\boxtimes}
{\save
[].[]*+[F--]\frm{}
\restore}
}
\end{aligned}
\quad\Rightarrow\quad
\begin{aligned}
\xymatrix@R=15pt@C=15pt{
{}&{}&{\phantom{\boxtimes}}\\
{\boxtimes}
{\save
[].[]*+[F--]\frm{}
\restore}
&{=}&{\boxtimes}
{\save
[].[]*+[F--]\frm{}
\restore}
}
\end{aligned}
\]
Или же данные могут перемещаться.
Например, модель присваивания Rust
\[
\begin{aligned}

{\save

{\save

\restore}
}
\end{aligned}
\quad\Rightarrow\quad
\begin{aligned}
\xymatrix@R=15pt@C=15pt{
{}&{}&{\phantom{\boxtimes}}\\
{\boxtimes}
{\save
[].[]*+[F--]\frm{}
\restore}

{\save
[].[]*+[F--]\frm{}
\restore}
}
\end{aligned}
\]
В C++ обычное присваивание копирует. Присваивание \verb"std::unique_ptr" и присваивание через \verb"std::move" перемещают, и это тоже value semantics.
Важное свойство такого подхода -- изменение данных в одном стакане никак не может повлиять на данные в другом.
Для элементарных типов такое поведение достигается тем, что они хранятся в разных областях памяти.
Однако, value semantics не означает, что это всегда так.
Например, \verb"shared_ptr" на константный объект тоже обладает value semantics.
Подумайте про работу с целыми числами в Python.
Вы ни за что не отличите ее от работы с целыми числами в C++.
Вы можете думать про такие переменные, как про стаканы с данными, и все будет работать.
Причина в том, что в Python целые числа всегда константы и присваивание просто переключает ссылку на объект с новым значением, не меняя старого.
Вы не можете вызвать ни одного метода у целых чисел, который бы их изменил.

\paragraph{Reference Semantics}

В Python переменные -- это имена, указывающие на данные.
Языки Java и C\# со смешанной семантикой (и это часто мешает), тем не менее их все же относят к языкам с reference semantics.
В них имена указывают на объекты классов. Примитивы копируются и обладают value semantics, а в C\# так же устроен \verb"struct".
Присваивание $x = y$ для такого имени означает: <<называй именем $x$ то, что называется именем $y$>>.
Модель присваивания в Python можно представлять себе так: 
\[
\begin{aligned}
\xymatrix@R=15pt@C=15pt{
{x}&{=}&{y}\ar[dl]\\
{}&{\boxtimes}&{}
}
\end{aligned}
\quad\Rightarrow\quad
\begin{aligned}
\xymatrix@R=15pt@C=15pt{
{x}\ar[dr]&{=}&{y}\ar[dl]\\
{}&{\boxtimes}&{}
}
\end{aligned}
\]
Очень важно понимать, что value semantics is safe by default.
А вот reference semantics -- контринтуитивная штука.

\paragraph{Тест на интуицию}

Предположим, нам дана матрица
\[
A = 
\begin{pmatrix}
{0}&{1}\\
{1}&{0}
\end{pmatrix}
\]
И пусть у нас есть следующий код:
\begin{pythoncode}
MatA = ...
# = A

print(Determinant(MatA))
print(Determinant(MatA))
\end{pythoncode}
Что выдаст эта программа?
Наша интуиция подсказывает, что должно быть $-1, -1$.
Однако, программа выдаст $-1, 1$.
Какая ваша первая мысль?
Наверное, есть баг в \verb"Determinant".
Каково же будет ваше удивление, когда вы проверите и убедитесь, что \verb"Determinant" работает полностью корректно.
Проблема в том, что \verb"Determinant" изменяет матрицу \verb"MatA", когда вычисляет определитель методом Гаусса.
Из-за этого во втором вызове у нас будет лежать единичная матрица.
Вот такая гадость.
Проблема в том, что человеческому сознанию сложно мыслить ссылками.
Мы мыслим значениями.
Потому мы не ожидаем такого поведения в этом коде.
И это главная проблема Python.
Это проявляется на изменяемых объектах. Для целых чисел, строк и кортежей ссылка ведет себя как значение, потому что объект нельзя изменить.
У этого подхода есть и плюсы, но value semantics я всё-таки люблю больше.
По сути, в языках с reference semantics переменные -- это \verb"shared_ptr" на необязательно константные объекты.
И если вы читали выше раздел~\ref{section::Dangerous}, подраздел~\ref{item::SharedPtr}, то знаете, почему они опасны.
Также рекомендую почитать раздел~\ref{section::SharedPtr}, посвященный \verb"shared_ptr".

\paragraph{Примеры в C++}

Давайте посмотрим с точки зрения семантики на следующие типы.
Я их специально поделил на типы с value semantics и reference semantics:
\begin{center}
\begin{tabular}{cc}
{\bf Value Semantics}&{\bf Reference Semantics}\\

{
\begin{minipage}[\baselineskip]{8cm}
\begin{cppcode}[numbers=none, linewidth=8cm]
char x;
A x;

const char& x; // almost
const A& x; // almost

const char* x; // almost
const A* x; // almost

std::unique_ptr<char> x;
std::unique_ptr<A> x;

std::shared_ptr<const char> x;
std::shared_ptr<const A> x;
\end{cppcode}
\end{minipage}
}&{
\begin{minipage}[\baselineskip]{8cm}
\begin{cppcode}[numbers=none, linewidth=8cm]



char& x;
A& x;

char* x;
A* x;




std::shared_ptr<char> x;
std::shared_ptr<A> x;
\end{cppcode}
\end{minipage}
}
\end{tabular}
\end{center}
Обратите внимание, что константные ссылки и указатели помечены как почти value semantics.
Дело вот в чем: если гарантируется, что в течение времени жизни ссылки или указателя объект будет жив и никто его не меняет через другое имя, то мы действительно имеем value semantics.
Например, такие гарантии есть, если
\begin{enumerate}
\item Строковые литералы
\begin{cppcode}
const char* msg = "Hello World!";
\end{cppcode}
Строковые литералы живут в статической памяти в течение времени жизни всей программы, и потому к ним безопасно получать доступ.

\item Передача аргументов в функцию.
Пока временный объект не забинжен на ссылку, его время жизни длится до конца полного выражения, которое его содержит.
Таким выражением является, например, вызов функции, в аргументы которого подставлен временный объект.
Например
\begin{cppcode}
struct A {
  const int& value() const {
    return value;
  }
  int value;
};

void f(const int& value);

int main() {
  f(A().value); // is OK
  f(A().value()); // is OK
}
\end{cppcode}

\item Продление life-time для объекта, который забиндили на const lvalue ссылку.
Тут стоит помнить вот такой пример:
\begin{cppcode}
struct A {
  const int& value() const {
    return value;
  }
  int value;
};

int main() {
  const int& x = A().value; // is OK (*@\cpplabel{sem-ref-ok-bind}@*)
  std::cout << x << '\n'; // is OK (*@\cpplabel{sem-ref-ok-use}@*)
  const int& y = A().value(); // is BAD (*@\cpplabel{sem-ref-bad-bind}@*)
  std::cout << y << '\n'; // y is dangling reference (*@\cpplabel{sem-ref-bad-use}@*)
}
\end{cppcode}
Если мы говорим об обычных ссылках, то время жизни временной структуры продлевается, если мы биндим ссылку на поле этой структуры (например строчки~\ref{sem-ref-ok-bind} и~\ref{sem-ref-ok-use} выше).
Однако, если ссылка получена через вызов метода (строчка~\ref{sem-ref-bad-bind}), а не связана с полем напрямую, то life-time для временного объекта не продолжается, и в строчке~\ref{sem-ref-bad-use} у нас \verb"y" является dangling reference, которая уже не ссылается на живой объект.
\end{enumerate}

\paragraph{Владение}

Value semantics дает понятие владения (ownership) очень естественным образом.
Ментальная модель такая: переменная -- это ящик с данными.
Когда вы задаете класс или структуру, вы указываете, что лежит в этом ящике:
\begin{cppcode}
struct A {
  std::string x;
  B y;
};
\end{cppcode}
В этом случае в ящике типа \verb"A" лежат два объекта типов \verb"std::string" и \verb"B".
И если вы уничтожаете ящик, то они умирают вместе с ним.
Если вы копируете или перемещаете ящик, то и они копируются или перемещаются вместе с ящиком.
Такое автоматическое владение само управляет временем жизни этих объектов, а не только scope внутри функции (раздел~\ref{section::RAII}).

\paragraph{ВАЖНО}

Код должен быть написан в value semantics всегда.
Тут полезно понимать, как переделать код со ссылками и указателями, чтобы у него была value semantics и при этом он не потерял в производительности и не стал жрать больше памяти, но этому надо будет научиться всего лишь один раз, а код будет лучше всегда.
